# Верхнеуровневые задачи MVP

Источник: [docs/tech-requirements.md](docs/tech-requirements.md).

Этот файл переводит техническое задание в крупные вертикальные задачи. Каждая задача должна уточняться перед реализацией по шаблону из ТЗ: сценарий, роли, сущности, статусы, деньги, даты, критерии приемки, edge cases и минимальная проверка.

## 1. Роли, доступ и seed администратора

Цель: расширить существующий auth-flow до ролевой модели `admin`, `manufacturer`, `user` и заложить единый механизм проверки прав.

Основной объем:

- роли и статус пользователя в Prisma schema, контрактах и auth DTO;
- seed первой учетной записи администратора для локальной разработки;
- backend guards для защищенных endpoint-ов;
- базовые админские операции со списком пользователей, ролями и блокировкой;
- web-состояния для входа, доступа и отказа в доступе.

Готово, когда:

- администратор создается локальным seed-скриптом;
- backend запрещает действия вне роли;
- пользователь, производитель и администратор получают только разрешенные данные;
- есть проверка блокировки пользователя;
- роль доступна клиентам через текущую сессию.

Минимальная проверка: backend integration tests на auth, роли, блокировку и error shape; typecheck backend/web.

Статус выполнения:

- Выполнено: добавлены роли `admin`, `manufacturer`, `user` и статусы `active`, `blocked`.
- Выполнено: роль и статус возвращаются через текущую сессию.
- Выполнено: добавлены backend guards и admin API для списка пользователей, смены роли и блокировки.
- Выполнено: добавлен безопасный локальный `seed:admin` без дефолтного пароля и с отзывом активных сессий.
- Выполнено: добавлен минимальный web-экран управления пользователями и отказ в доступе для non-admin.
- Проверено частично: typecheck backend/web/mobile, backend unit tests и web tests прошли; Docker-backed integration/E2E нужно прогнать при доступном Docker daemon.

## 2. Производители и модерация профиля

Цель: дать производителю возможность зарегистрироваться, заполнить профиль и пройти административную модерацию.

Основной объем:

- сущность профиля производителя и статусы `draft`, `moderation`, `approved`, `rejected`, `blocked`;
- контракты и API для профиля текущего производителя;
- админские API для списка производителей и смены статуса;
- web-кабинет производителя для профиля и статуса модерации;
- админский экран модерации производителей.

Готово, когда:

- производитель может создать и обновить свой профиль;
- производитель не видит чужие профили;
- администратор видит список производителей и меняет статус;
- заблокированный или неутвержденный производитель ограничен в дальнейших действиях;
- UI показывает loading, empty, error и success-состояния.

Минимальная проверка: backend integration tests на права производителя и администратора; client/API smoke для основного сценария.

Статус выполнения:

- Выполнено: добавлена модель профиля производителя со статусами `draft`, `moderation`, `approved`, `rejected`, `blocked`.
- Выполнено: добавлены контракты и API текущего производителя для чтения, сохранения черновика и отправки на модерацию.
- Выполнено: добавлены админские API и web-экран модерации производителей со сменой статусов.
- Выполнено: добавлен web-кабинет производителя на shadcn/UI с компонентной формой профиля и состояниями loading, empty, error, success, disabled.
- Выполнено: заблокированный профиль нельзя менять или отправлять, утвержденный профиль нельзя повторно отправить без редактирования.
- Проверено: backend unit/typecheck/prisma validate, backend integration на `DATABASE_URL_TEST`, web tests/typecheck/lint/build и Playwright E2E прошли.

## 3. Велосипеды, модерация и публичный каталог

Цель: реализовать карточки велосипедов, производительское управление ими, модерацию и публичный каталог доступных позиций.

Основной объем:

- модель велосипеда с размерами, ценами, залогом, техническими параметрами, городом, доставкой и safety notes;
- статусы велосипеда и moderation flow;
- API производителя для создания, редактирования и отправки на модерацию;
- admin API для списка, статуса и решения по модерации;
- публичный каталог и карточка велосипеда с фильтрами по размеру, цене, датам и доступности.

Готово, когда:

- производитель управляет только своими велосипедами;
- публичный каталог показывает только `available` и прошедшие модерацию велосипеды;
- фильтры каталога работают с пагинацией и стабильной сортировкой;
- карточка показывает цену, залог, технические ограничения и условия получения;
- администратор может скрыть, архивировать или отправить велосипед в обслуживание.

Минимальная проверка: schema validation, backend tests на права и фильтры, web smoke каталога и карточки.

Статус выполнения:

- Выполнено: добавлена модель велосипеда с размерами, ценами в копейках, залогом, техническими параметрами, доставкой, статусами и безопасным `photoUrls` default.
- Выполнено: добавлены контракты и API производителя для списка с пагинацией, создания, редактирования и отправки велосипеда на модерацию.
- Выполнено: добавлены admin API и shadcn/UI экран модерации велосипедов со статусными переходами, disabled-state правилами и защитой от публикации велосипедов неутвержденных производителей.
- Выполнено: публичный каталог и карточка показывают только `available` велосипеды утвержденных производителей, поддерживают фильтры по размеру, цене, городу и date-only параметры до появления заказов.
- Выполнено: закрыты race/edge cases для создания, публикации, скрытия, обслуживания, архивации, редактирования опубликованной карточки и блокировки производителя.
- Проверено: backend unit/typecheck/prisma validate, backend integration на `DATABASE_URL_TEST`, web tests/typecheck/lint/build и Playwright E2E прошли.

## 4. Создание заявки на аренду

Цель: дать пользователю возможность выбрать один или несколько велосипедов, даты, способ получения и создать заявку со снимками цен.

Основной объем:

- сущности заказа и позиций заказа;
- date-only правила `YYYY-MM-DD`, включительный расчет дней и минимальный срок 1 день;
- расчет аренды, залога, доставки и итоговой суммы на backend;
- фиксация snapshots цены и залога в `OrderItem`;
- форма заявки в web с контактами, доставкой и согласием с правилами безопасного использования.

Готово, когда:

- пользователь создает заказ в статусе `request`;
- суммы считаются backend-ом в копейках и не зависят от клиента;
- изменение карточки велосипеда не меняет уже созданный заказ;
- заявка не создается без валидных дат, контактов и safety agreement;
- пользователь видит созданную заявку в личном кабинете.

Минимальная проверка: unit tests на даты и суммы; backend integration tests на создание заявки; web smoke формы.

Статус выполнения:

- Выполнено: добавлены сущности заказа и позиций заказа со статусом `request`, типом получения и snapshot-полями велосипеда/производителя.
- Выполнено: date-only правила `YYYY-MM-DD`, включительный расчет дней, лимит периода и backend-guard от переполнения сумм вынесены в контракты и backend.
- Выполнено: backend считает аренду, залог, доставку и итог в копейках, не принимает клиентские money fields и фиксирует snapshots цены/залога в `OrderItem`.
- Выполнено: web-заявка на shadcn/UI позволяет выбрать велосипеды из каталога, указать даты, получение, контакты и safety agreement; после успешного создания форма блокируется от повторной отправки.
- Выполнено: пользователь видит свои заявки в списке и деталях; чужие заявки скрыты owner-scoped доступом.
- Проверено: backend unit/typecheck/prisma validate, backend integration на `DATABASE_URL_TEST`, web tests/typecheck/lint/build и Playwright E2E прошли.

## 5. Административное подтверждение заявки и доступность

Цель: реализовать безопасное подтверждение или отклонение заявки администратором с проверкой конфликтов доступности.

Основной объем:

- проверка пересечения периодов по заказам `confirmed` и `issued`;
- транзакционная защита от гонки двух подтверждений;
- переходы `request -> confirmed` и `request -> cancelled`;
- история статусов с автором, временем и комментарием;
- админский экран деталей заявки с предупреждениями по ограничениям велосипеда.

Готово, когда:

- администратор подтверждает только заявки с доступными велосипедами;
- конфликтующая заявка отклоняется или не подтверждается с доменным кодом ошибки;
- пользователь может отменить только свою заявку до подтверждения;
- история статусов пишется на каждый переход;
- UI ясно показывает причину отказа и следующий шаг.

Минимальная проверка: backend integration tests на конфликты дат, права и переходы статусов; focused UI smoke админского действия.

Статус выполнения:

- Выполнено: добавлена история статусов заказов с автором, временем и комментарием, связанная с заказом и пользователем.
- Выполнено: подтверждение `request -> confirmed` проверяет live-состояние велосипеда, статус производителя, доставку и включительные пересечения дат только с `confirmed`/`issued` заказами.
- Выполнено: гонки подтверждений сериализуются транзакцией PostgreSQL/Prisma, retry и per-bike `availabilityLockVersion`; повторные переходы не создают дубли history.
- Выполнено: администратор видит список и детали заявок на shadcn/UI, предупреждения по доступности/ограничениям, историю и actions confirm/cancel с disabled/error/success состояниями.
- Выполнено: пользователь может отменить только свою заявку в статусе `request`; чужие и уже подтвержденные заявки защищены backend-ом.
- Проверено: backend unit/typecheck/prisma validate, backend integration на `DATABASE_URL_TEST`, web tests/typecheck/lint/build и Playwright E2E прошли.

## 6. Платежные заглушки аренды и залога

Цель: добавить MVP-платежи без реального эквайринга, сохранив архитектурную возможность заменить провайдера позже.

Основной объем:

- сущность платежа с типами `rent` и `deposit`, провайдером `stub` и статусами;
- API создания платежей только для подтвержденного заказа;
- dev endpoints успешного и ошибочного завершения платежа;
- идемпотентность повторного успешного завершения;
- конфигурация включения stub provider и запрет dev endpoints в production по умолчанию;
- отображение платежных статусов пользователю и администратору.

Готово, когда:

- для заказа может быть только один активный платеж каждого типа;
- сумма платежа совпадает со снимком суммы заказа;
- failed/cancelled попытку можно повторить;
- dev endpoints отключаются конфигурацией;
- заказ нельзя выдать без успешных платежей аренды и залога.

Минимальная проверка: backend integration tests на платежные инварианты; env/config tests; web smoke платежного сценария.

Статус выполнения:

- Выполнено: добавлена сущность `Payment` с типами `rent`/`deposit`, provider `stub`, статусами `pending`/`succeeded`/`failed`/`cancelled`, снимком суммы, валютой, completion metadata и Prisma-ограничением одного активного платежа на заказ и тип.
- Выполнено: пользователь может создать платеж только для своего подтвержденного заказа; повторный create возвращает существующую активную попытку, failed/cancelled освобождают retry, zero deposit сразу становится successful.
- Выполнено: dev endpoints `stub-success`/`stub-fail`/`stub-cancel` доступны только при включенном конфиге, repeated success идемпотентен, terminal failed/cancelled требуют новой попытки.
- Выполнено: production defaults отключают stub provider/dev endpoints, `.env.example` отражает платежную конфигурацию без реальных секретов.
- Выполнено: пользователь и администратор видят платежные статусы через компонентный shadcn/UI payments-модуль; админ видит отдельный список платежей и blocker выдачи до полной оплаты.
- Выполнено: task 6 экспонирует `paymentRequirementsMet` и явно не открывает `issued` transition; фактический guard выдачи остается владельцем задачи 7.
- Проверено: backend unit/typecheck/prisma validate, backend integration на `DATABASE_URL_TEST`, web tests/typecheck/lint/build и Playwright E2E прошли; review loop достиг оценки 9.5/10.

## 7. Выдача, возврат и чеклисты

Цель: закрыть операционный цикл заказа от подтверждения до возврата велосипеда с фиксацией состояния.

Основной объем:

- переходы `confirmed -> issued`, `issued -> returned`, `confirmed -> cancelled`;
- чеклисты выдачи и возврата по конкретному заказу и велосипеду;
- административные формы чеклистов;
- перевод велосипеда в обслуживание или скрытие из каталога при проблемах безопасности;
- история статусов заказа и связанных операций.

Готово, когда:

- выдача невозможна без успешной оплаты аренды и залога;
- возврат невозможен без статуса `issued`;
- чеклист связан с конкретным заказом, велосипедом и автором;
- администратор видит и заполняет issue/return чеклисты;
- повреждения или небезопасные условия могут вывести велосипед из каталога.

Минимальная проверка: backend integration tests на переходы и чеклисты; web smoke админского issue/return flow.

Статус выполнения:

- Выполнено: добавлены чеклисты выдачи и возврата по заказу, велосипеду, типу операции, автору и времени проверки.
- Выполнено: переход `confirmed -> issued` требует успешные rent/deposit платежи, полный issue checklist, актуальный live-status велосипеда и утвержденного производителя; велосипеды атомарно переходят в `rented`.
- Выполнено: переход `issued -> returned` требует return checklist и live-status `rented`; clean return возвращает велосипед в `available`, safety findings переводят в `maintenance` или `hidden`.
- Выполнено: общий admin status update велосипедов не может обойти return checklist для `rented`; ручные изменения `rented` статуса заблокированы backend-ом и не показываются в UI.
- Выполнено: админский UI на shadcn/UI вынесен в компонент чеклистов, показывает историю проверок, блокеры выдачи и invalidates связанные order/payment/bicycle/catalog caches.
- Выполнено: чеклисты создаются атомарно внутри status transition API, чтобы статус заказа и состояние велосипеда не расходились.
- Проверено: backend unit/typecheck/prisma validate, backend integration на `DATABASE_URL_TEST`, web tests/typecheck/lint/build и Playwright E2E прошли; review loop достиг оценки 9.6/10.

## 8. Личный кабинет пользователя

Цель: собрать пользовательский кабинет для просмотра заявок, заказов, платежей, контактов и условий получения/возврата.

Основной объем:

- список текущих и исторических заказов пользователя;
- детальная карточка заказа;
- статусы заказа и платежей;
- отмена заявки до подтверждения;
- повторное создание платежа после неудачной попытки, если это разрешено backend-ом.

Готово, когда:

- пользователь видит только свои заказы;
- статусы заказа и платежей актуальны после обновления данных;
- отмена доступна только в разрешенном статусе;
- ошибки API дают понятный следующий шаг;
- обработаны loading, empty, error, success и disabled-состояния.

Минимальная проверка: backend access tests; web client tests или focused Playwright smoke для кабинета.

Статус выполнения:

- Выполнено: пользовательский список заказов разделен на `current`, `history` и `all` через контрактные scope/status правила, с owner-scoped backend-фильтрацией и валидацией несовместимых/неизвестных параметров.
- Выполнено: детальная карточка заказа на shadcn/UI показывает позиции, суммы, получение/возврат, контакты, статусы заказа и платежей, следующий шаг и privacy-safe ошибки.
- Выполнено: отмена заявки доступна только в статусе `request`, платежные действия сбрасывают устаревшие ошибки между retry/success, а повторные платежи используют существующие backend-инварианты.
- Выполнено: публичный `OrderDto` не раскрывает `adminComment`; поле осталось только в admin DTO, а raw HTTP tests проверяют отсутствие этого поля в пользовательских detail/list ответах.
- Выполнено: клиентский кабинет вынесен в компонентный модуль на shadcn/UI primitives, query keys учитывают пользователя, а session cache cleanup удаляет list/detail заказы между аккаунтами.
- Проверено: backend unit/typecheck/prisma validate, backend integration на `DATABASE_URL_TEST`, web tests/typecheck/lint/build и Playwright E2E прошли; review loop достиг оценки 9.7/10.

## 9. Кабинет производителя

Цель: дать производителю рабочее место для профиля, своих велосипедов и заказов по ним без раскрытия лишних персональных данных.

Основной объем:

- список своих велосипедов и статусов модерации;
- создание, редактирование и отправка велосипеда на модерацию;
- просмотр заказов, связанных со своими велосипедами;
- ограниченный DTO заказа для производителя;
- история выдачи и возврата по своим велосипедам.

Готово, когда:

- производитель не может читать или менять чужие велосипеды;
- производитель видит только связанные заказы;
- персональные данные арендатора ограничены данными, нужными для исполнения аренды;
- нельзя менять архивированные или запрещенные статусом карточки вне правил;
- кабинет показывает пустые и ошибочные состояния.

Минимальная проверка: backend integration tests на producer scoping и DTO; web smoke кабинета производителя.

Статус выполнения:

- Выполнено: существующие страницы профиля и управления велосипедами производителя сохранены, добавлен отдельный раздел связанных заказов производителя.
- Выполнено: добавлены contracts, API и backend service для `/api/manufacturer/orders` и `/api/manufacturer/orders/:id` с отдельным `ManufacturerOrderDto`, не переиспользующим admin DTO.
- Выполнено: producer-scoping заказов построен по snapshot-полю `OrderItem.manufacturerProfileIdSnapshot`; detail несвязанного заказа возвращает `404`.

## 10. Админ-панель и быстрые фильтры

## 13. Сквозной Playwright happy-path

Цель: покрыть главный пользовательский сценарий через настоящий backend и web UI.

Основной объем:

- подготовка тестовых данных или seed для администратора, производителя и велосипедов;
- сценарий регистрации/входа;
- просмотр каталога и создание заявки;
- административное подтверждение;
- прохождение платежей аренды и залога через заглушки;
- выдача, возврат и проверка финального статуса.

Готово, когда:

- E2E проходит через реальные API, БД и Vite UI;
- сценарий не зависит от ручных действий;
- тест использует стабильные селекторы и repo E2E-инфраструктуру;
- негативные матрицы остаются в backend tests, а Playwright проверяет happy-path;
- артефакты теста остаются в существующих E2E artifact-директориях.

Минимальная проверка: `bun run e2e:web`; при изменении контрактов также `bun run typecheck` и релевантные backend tests.

## Сквозные требования для всех задач

- Контракты API описывать в `packages/contracts` через Zod и использовать на backend/web сторонах.
- Бизнес-логику держать в backend service layer, routes оставлять тонкими.
- Prisma schema менять декларативно и генерировать миграции стандартным workflow репозитория.
- Деньги хранить целыми числами в минимальных единицах валюты.
- Даты аренды считать date-only значениями, не полагаясь на timezone клиента.
- Любое изменение ролей, статусов, денег, дат или доступности проверять на producer и consumer сторонах.
- Для UI обрабатывать loading, empty, error, success, disabled и защиту от двойной отправки.
- Не реализовывать в MVP реальные платежные провайдеры, уведомления, мобильное приложение, автоматическую логистику и юридические интеграции.
